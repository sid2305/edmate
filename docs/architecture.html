Edmate build architecture

16 Oct 2026 · Siddhant Lahoti · lives in docs/architecture.html

Edmate is built by a team of AI agents in Claude Code. One main session leads; specialist agents from ECC plan, write, test and review each task. The team lead merges PRs itself once a merge gate passes; you decide only risky or ambiguous calls, and every decision is logged.

1. At a glance

The setup turns the 94 tasks in the build plan (v0.3) into reviewed, merged code, with a human in charge of every risky call.

What it builds

Edmate v0.3: teachers turn their knowledge into an AI teaching agent and sell packages; students subscribe and learn with it. The agent first, then the teacher studio, student app and payments (docs/edmate-harness-build-plan.md).

Who builds it

22 agents: 19 copied from ECC, 3 written for Edmate. Only those a phase needs are added.

How work moves

Board → plan → build → review → gates → merge gate → merge. Agents hand over through files, not chat.

What keeps it safe

Hooks and the merge gate enforce the rules. You approve only risky PRs: child safety, contracts, keys, data.

What gets recorded

Every decision the spec did not make, in plain words, in docs/decisions/log.md.

Where it lives

Only inside ~/edmate. Nothing global, so other projects are untouched.

2. The building blocks

Claude Code has six kinds of building block. Only hooks and an agent's tool list are enforced; the rest is guidance the model reads.

BlockWhat it is, in simple wordsLoaded whenEnforced?
CLAUDE.mdThe project's standing brief: what Edmate is, the rules, where things liveEvery sessionNo, guidance
.claude/rules/Extra rules for one part of the code, e.g. "harness code never imports the database"Only when working on matching filesNo, guidance
.claude/agents/A specialist with its own job, allowed tools and model. Works in its own context, returns a short resultWhen the lead hands it a jobIts tool list, yes
.claude/skills/A playbook or body of know-how, e.g. test-first developmentWhen relevant; until then only its one-line description is visibleNo, guidance
.claude/hooks/Small scripts Claude Code runs before or after every file edit and shell commandAlways, automaticallyYes
.mcp.jsonConnections to outside tools, e.g. Context7 for current library docsAt startup—

One rule of Claude Code shapes everything below: an agent cannot start another agent. So the main session is always the team lead, and every handoff passes through it.

3. The big picture

You talk only to the team lead. The lead reads the board, hands one job at a time to a specialist, and collects the result from a file.

4. Where it comes from: ECC

ECC (MIT licence) is a large, community-built Claude Code setup. We use it as a library: we copy the parts each phase needs and leave the rest.

How ECC is built

LayerWhat it holds
Source71 agents, 311 skills, 97 commands, 27 hooks, rules for about 20 languages
ManifestsGroup the source into 33 modules and 7 install profiles (minimal, core, developer, security, research, full, OpenCode)
Installerinstall.sh copies a profile into ~/.claude/, or the plugin installs it with ecc: names
AdaptersConfig folders for about 15 other AI coding tools (Cursor, Codex, Gemini and more)
ecc2/An alpha Rust dashboard for many sessions at once: SQLite session store, worktree-aware sessions

What we take

  • 19 agents and 29 skills, copied phase by phase (sections 5 and 6).
  • The phase pipeline: research → plan → build → review → verify, each phase writing a file the next one reads.
  • Worktrees for parallel work: one builder per git worktree, no overlapping files, at most 3 at once.
  • Task cards with merge gates, from team-agent-orchestration: owner, scope, state, evidence, gate.
  • The "collect your own results" rule: whoever delegates must wait and integrate, never end on "waiting".

What we leave out, and why

  • The full install. ~400 items you would not use, all listed in every session (chart below).
  • Generic rules that clash with the build plan, e.g. 80% coverage everywhere where the plan demands 100% for the simulator and guards.
  • "Use PROACTIVELY" wording in agent descriptions, which makes agents start without being asked. We remove it when copying.
  • Global hooks that would run in every project on your laptop.

7. How one task flows

Every task takes the same seven steps. Two loops send work back and end with you only if they repeat; risky PRs wait for your label at the last step.

8. Merge policy

The team lead merges PRs itself. It holds the full picture (PRD, build plan, board, every handoff), so it checks the gate and decides. You are asked only when a change is risky or the spec is unclear.

TierWhat falls in itWho merges
NormalMost tasks: pipeline steps, routes, UI, tests, toolingTeam lead, after the merge gate
RiskyStudent safety (guardrails, prompt packs, skill and persona templates, safety and locked evals, alerts) · the access filter · payments, subscriptions and webhooks · frozen contracts and ADRs · keys, sign-in, each teacher's and student's data kept apart · migrations that drop or delete data · .claude/ and .github/ configYou add the human-approved label, then the lead merges
AmbiguousUnclear or conflicting spec, or a trade-off that changes how the product behavesThe lead asks you before building, and logs your answer
ReviewerPlatform prompt packs, skill templates and eval casesA named person signs off in reviewed_by. Teachers own and review their own course material

The merge gate: all must hold

  1. Reviews ran: code-reviewer and typescript-reviewer, plus the specialist for the area, plus safety-reviewer when safety code changes.
  2. Every CRITICAL and HIGH finding is fixed, and a reviewer re-ran its checks to confirm it. The builder's word is not enough.
  3. MEDIUM and LOW findings are fixed, deferred to a new board task, or marked won't-fix with a decision-log entry saying why.
  4. CI and eval gates are green.
  5. Decisions are written down in the handoff (or "None").
  6. merge_gate.py passes. It reads review.md and handoff.md from the branch and the list of changed files, then answers PASS, FAIL or NEEDS HUMAN.

The gate's risky list lives in .claude/skills/merge-gate/risk-paths.txt; the architect updates it as code lands. The gate was tested on 16 Oct 2026 against six cases: a clean pass, an open HIGH finding, changes requested, a missing safety review, risky code, and a migration that drops a column.

9. Decision log

Every decision the spec did not already make is written down in plain words in one file: docs/decisions/log.md, newest first. You can read it whenever you like.

  • What gets logged: a library choice, a data shape, a trade-off, how an unclear line was read, a deviation from the plan, a finding left unfixed, and every answer you give.
  • What does not: naming and formatting.
  • Who writes it: agents note decisions in their task's handoff; the team lead copies them in when the PR merges. One writer on main means no merge conflicts.
  • How to skim it: each entry has a risk level. medium entries are the ones worth a look; high ones are yours.

10. Running tasks in parallel

Up to 3 builders run at once. Each gets its own git worktree (a separate copy of the repo on its own branch), so they never overwrite each other.

  • Different folders per lane. Two tasks that edit the same package wait for each other.
  • No lane edits the contracts. packages/contracts is frozen after task 0.3.
  • One integrator. Only the team lead merges, one PR at a time, and re-runs the gate on the next PR after rebasing it.

11. The task board

The board (docs/board/tasks.yaml) holds all 94 tasks of plan v0.3, their dependencies, each task's risk tier (30 risky, 1 needing a named reviewer) and 12 open human decisions. A task starts only when its dependencies are done and its decisions are answered.

The lead drives the board with one small script:

python3 .claude/skills/board/board.py next            # ready tasks, and tasks waiting on a decision
python3 .claude/skills/board/board.py status          # counts, work in progress, open decisions
python3 .claude/skills/board/board.py show 3.5        # one task
python3 .claude/skills/board/board.py set 3.5 running --branch m3/3.5-help-ladder
python3 .claude/skills/board/board.py decide licence "MIT"

13. GitHub and Actions

The code lives in a public GitHub repo under the MIT licence. Agents act through a private GitHub App (edmate-bot), never your account, and GitHub Actions enforces the merge rules on every PR. The workflows arrive with task 0.5; setup steps are in docs/setup/github.md.

WorkflowWhat it doesWhen
CI gatesTypecheck, lint, tests and eval suites on replayed model responses, so no API keys are neededEvery PR (task 0.5)
Merge-gate checkRuns merge_gate.py --pr; a required check, so GitHub itself refuses a merge that fails itEvery PR (task 0.5)
Secret scanRuns .githooks/secret-scan.py --all; a required check, beside GitHub's own secret scanning and push protectionEvery PR (task 0.5)
Risk labelsLabels a PR needs-human when it touches a risky path, so you only open thoseEvery PR (task 0.5)
Nightly live evalsRuns the eval suites against real models with a provider key stored as a GitHub secretLater (task 7.4)
Decision-log pageRebuilds a readable page from docs/decisions/log.md on every mergeOptional

Keeping private things out of a public repo

Anything pushed to a public repo can be copied within minutes, so there are five layers, and a leaked key is always rotated, never just deleted.

  1. .gitignore keeps .env files, keys, local databases and Claude's local state out of git.
  2. Claude Code hooks stop an agent writing a key file, and scan every file it edits.
  3. A git pre-commit hook runs the same scan on everything staged, so a commit with a secret never happens.
  4. CI runs the scan again on every PR (task 0.5).
  5. GitHub secret scanning and push protection reject known key formats at push time.

Commits in this repo use your private GitHub address (…+sid2305@users.noreply.github.com), not your Gmail. Your global git settings are unchanged. Your name does appear in the licence and the doc bylines, which is normal for open source.

The bot

  • Why a GitHub App: GitHub can then tell agent actions from yours. Only you can add human-approved, and the merge-gate check confirms the label came from you.
  • Its key lives outside the repo, in ~/.edmate-bot/, and is turned into a 1-hour token for each push or PR.
  • It cannot bypass the main ruleset; only you are on the bypass list.

14. Build timeline

The teacher's agent comes first, including the access filter, and must pass the exit gate with zero locked-content leaks. Payments and the trust console run alongside; the studio and student app start after the gate.
