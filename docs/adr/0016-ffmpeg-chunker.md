# ADR-0016: An ffmpeg chunker in the worker, for MP4/WebM/M4A recordings of any length

## Status

Accepted (27 Oct 2026). Task 11.4d (board 11.4d). Reviewed by architect, security-reviewer and typescript-reviewer (one fix round, re-verified by all three); the lead approved it with a `risk: high` decision.

## Date

2026-10-27

## Context

- `createWhisperTranscriber`'s `defaultChunker` (`packages/gateway/src/transcriber/chunking.ts`) only splits WAV and MP3 recordings over Whisper's 24 MB upload limit; an M4A, MP4 or WebM recording over that limit fails downstream as `input_too_large` even though `apps/web`'s media cap is 500 MB. Task 11.4b (done) refused those three types at upload with a fixed message pointing to MP3 or a transcript file, as a stopgap, and filed this task as the real fix (the gap found while planning 11.4, see `docs/tasks/11.4/plan.md`, "Gap this task closes").
- `apps/web/src/studio/files.ts`'s `UploadType` table already names exactly the three types the worker can't split today: `audio/mp4` (.m4a), `video/mp4` (.mp4), `video/webm` (.webm) -- each currently `splittable: false` and capped at 24 MB at upload (task 11.4f; this task does not touch that table or that cap, a follow-up).
- Splitting these formats generally needs decoding compressed audio (and, for MP4/WebM, discarding any video stream) before cutting it on a byte boundary that stays exact across bit depths and channel counts -- unlike WAV/MP3, which `defaultChunker` already parses and cuts without re-encoding. `apps/worker`'s Docker image gains a system binary (`ffmpeg`) it did not have before: a tech-stack change (rule 2), reviewed by architect, security-reviewer and typescript-reviewer, approved by the lead with a `risk: high` decision.
- `createWhisperTranscriber` already accepts an optional `chunker` and already enforces `maxUploadBytes`, timeouts and chunk-order checks (`checkChunks`) around whatever a chunker returns (`packages/gateway/src/transcriber/whisper.ts`). This task supplies a chunker, not new plumbing there. `DEFAULT_MAX_DOWNLOAD_BYTES` (600 MB) and `TranscriberError` are already exported from `@edmate/gateway` and are reused, not duplicated.

## Decision

1. **Where it lives.** A new `AudioChunker` (the existing port type, unchanged) in `apps/worker/src/ingest/ffmpegChunker.ts`, exported as `createFfmpegChunker(opts?)`. Not in `packages/gateway`: the binary is specific to this one deployable image, and `packages/gateway` already exports every type and constant the new code needs. Composed only at `apps/worker/src/ingest/gateway.ts`'s `createIngestGateway` (Phase B).
2. **Scope.** Exactly the three types `apps/web`'s `UploadType` table already names: `audio/mp4`, `video/mp4`, `video/webm`. `audio/mpeg` and `audio/wav` (and anything else) go straight to the existing, already-tested `defaultChunker`, unchanged -- `createFfmpegChunker` wraps it: it only runs ffmpeg for its own three types and delegates every other type to `defaultChunker`, including that chunker's own `input_too_large` refusal for an unsupported type.
3. **How it splits.** Audio only, always re-encoded to a fixed, known format -- 16 kHz mono 16-bit PCM WAV -- so byte-rate math is exact and no general-purpose container parsing is needed on the output side. One `ffmpeg` process per call does transcode *and* split in one pass, using the `segment` muxer with a `segment_time` computed from `maxBytes` and the fixed 32,000 bytes/second rate (`floor((maxBytes - headerSlack) / 32000)` seconds per piece, minimum one second), writing numbered whole WAV files (each with its own valid header) to a per-call temp directory. The chunker reads them back in filename order, computes each piece's `offsetMs` as the running total of the pieces already read (not `index * segment_time`, so the last, shorter piece is exact) and its `durationMs` from its own `data` chunk size, using a small, local, generic RIFF/`data`-chunk reader written fresh in this file (not imported from `packages/gateway`, which stays untouched). `-vn` drops any video stream -- only audio is decoded or written. The input file is **never** probed by content: `-protocol_whitelist file` (so ffmpeg can only ever open local files, never dial a network address) and a forced input demuxer (`-f mp4` for `audio/mp4`/`video/mp4`, `-f webm` for `video/webm`, picked from a fixed table keyed by the caller's mime type -- the mime string itself is never interpolated into the argv) both precede `-i`, so a file shaped like an HLS playlist (`#EXTM3U` with a remote segment URL) or an ffconcat playlist referencing another local file is rejected outright as invalid data for the forced container, rather than ffmpeg auto-detecting and following it (fix round 1, 27 Oct 2026: security-reviewer CRITICAL, architect HIGH).
4. **No shell, no argument injection.** `child_process.spawn('ffmpeg', [...fixedArgs], { shell: false })` (the default) -- every argument is either a literal flag, the fixed-table demuxer name for the caller's mime type, or a path the chunker created itself (`fs.mkdtemp` under `os.tmpdir()`), never a string built from the recording's bytes, mimeType or any request field. The chunker never uses `exec`/`execSync` or a template string; `mimeType` and the raw input bytes never appear in the argv.
5. **Resource limits.**
   - Input size is already capped upstream (`maxDownloadBytes`, 600 MB, enforced by `whisper.ts` before the chunker is ever called) -- unchanged.
   - A hard wall-clock timeout per ffmpeg process (default 10 minutes, matching the existing `DEFAULT_CHUNK_TIMEOUT_MS`/`DEFAULT_DOWNLOAD_TIMEOUT_MS` precedent): on abort, the runner sends SIGTERM itself and starts a short grace timer (a few seconds, overridable for tests); if the process hasn't exited by then (an ffmpeg build that ignores or is stuck past reacting to SIGTERM), it escalates to SIGKILL, so a hung or adversarial input can never hang the (concurrency-1) ingest worker indefinitely even past the first signal (fix round 1, 27 Oct 2026: typescript-reviewer HIGH -- `spawn`'s own `signal` option rejects the moment the signal aborts without confirming the child actually exited, which would have let this bug through undetected). A timeout maps to a retryable `TranscriberError('provider_error', true, ...)`, matching the existing download-timeout convention.
   - A running total of the bytes written across all produced pieces is checked (via `fs.stat`, before each piece's bytes are read) against `DEFAULT_MAX_DOWNLOAD_BYTES` (reused, not duplicated) as pieces are read back, in case a small input decodes to an implausibly long or loud stream (a decompression-bomb shape); exceeding it throws a non-retryable `input_too_large` and stops reading further pieces.
   - `-nostdin` so ffmpeg never blocks waiting for interactive input; stdout/stderr are piped and drained while the process runs but never read into a string or logged (only the exit code and a fixed message reach any log line or error, per the existing "never log the signed URL" convention in `source.ts`/`whisper.ts` -- the same discipline extends to ffmpeg's stderr, which could otherwise be made to contain attacker-chosen bytes from the input file's metadata).
   - **Cleanup.** The per-call temp directory (`fs.mkdtemp`) is removed with `fs.rm({ recursive: true, force: true })` in a `finally` block that runs on every exit path: success, a non-zero ffmpeg exit code, a timeout kill, or the output-size guard tripping.
   - **Concurrency.** The ingest `Worker` is already `concurrency: 1` per worker process (`apps/worker/src/ingest/workers.ts`); this task adds no new concurrency control. N worker replicas run up to N ffmpeg processes at once.
6. **Errors.** A non-zero ffmpeg exit, or no output pieces at all (e.g. silence shorter than one segment, or a zero-length stream), is a non-retryable `TranscriberError('validation', false, 'the recording could not be read by the chunker')` -- the same "a chunker never guesses" convention `chunking.ts`'s own comment already states, and never an empty success.
7. **The Dockerfile (Phase B).** One line in the `runtime` stage of `apps/worker/Dockerfile`, before `USER node`: `RUN apk add --no-cache ffmpeg`, with a comment pointing at this ADR. Reproducibility comes from the already-pinned base image tag (`node:22.22.3-alpine3.22`), the same way every other dependency in that Dockerfile is pinned; `apk` itself has no per-package digest pin, a known, accepted gap, not new to this task. The builder writes this line and does not run `docker build` (Allowed tools; builders never run docker/compose beyond throwaway test containers per this task's plan). The lead or a human runs the actual build once and checks `ffmpeg -version`'s licence banner before relying on this in a deployed image (follow-up board task 11.4i).
8. **Licence.** ffmpeg's own code is LGPL 2.1+; a build configured `--enable-gpl` (to add GPL-licensed codecs such as libx264/libx265) makes the *resulting binary* GPL as a whole. Edmate only needs audio decode (AAC, Opus/Vorbis, the codecs MP4/WebM/M4A commonly carry) and a WAV (PCM) encode -- no GPL-only codec is required, and ffmpeg always runs as a separate process here, never linked into Edmate's own code. Whether Alpine's `ffmpeg` apk package in the pinned base image is built `--enable-gpl` is not yet verified; this ADR records the decision to default to the distribution package unless that check fails, with a documented fallback (a pinned, checksum-verified LGPL-only static build) if it does. The human licence check of the built image is tracked on follow-up task 11.4i, not this task.
9. **Image size.** The Alpine `ffmpeg` package pulls shared libraries for codecs this task never calls (video encoders, subtitle burn-in, etc.); this is accepted for MVP speed. A smaller, feature-pruned static build is a size optimisation for later, not blocking this task.

## Alternatives

- **A pure-JS/WASM demuxer-decoder** (e.g. an ffmpeg-to-WASM build, or per-container JS demuxers plus JS/WASM AAC/Opus decoders). Not chosen: it is slower, raises the same codec-licence question without the benefit of a well-audited OS package, is harder to bound with a process-level timeout/kill, and for MP4/WebM/Opus/AAC specifically ends up being "ffmpeg's own decoders, recompiled" rather than a genuinely different, lighter dependency.
- **A hosted transcoding/transcription service** (e.g. a cloud media API). Not chosen: a new paid vendor (payments are out of scope until M10 per the team-lead's "Payments come last"), recordings can carry students' voices and names (11.4's privacy concern) which would now leave Edmate's infrastructure, and the extra network hop works against the 15-minute budget this pipeline is already tight on.
- **ffmpeg as a separate sidecar/microservice** instead of inside the worker image. Not chosen for MVP: a second deployable, a network call and its own auth add real operational cost for one binary call per recording; revisit only if image size or process isolation becomes a measured problem.
- **ffmpeg's `segment` muxer sized by a fixed duration guess** instead of computed from `maxBytes` and the fixed WAV byte rate. Not chosen: a fixed duration can't guarantee pieces stay under Whisper's upload cap for every bit depth/channel combination; computing from the byte rate we ourselves fix (16 kHz mono 16-bit) keeps the guarantee exact, the same discipline `splitWav` in `chunking.ts` already uses.
- **Piping ffmpeg's stdin/stdout instead of temp files.** Not chosen: MP4's index (`moov` atom) can sit at the end of the file, which many decoders (including ffmpeg's `mov` demuxer, depending on how the file was written) need to seek to read, so a non-seekable stdin pipe doesn't work in general; the `segment` muxer's numbered output files are also simplest to read back by name, which piping would complicate rather than simplify.

## Consequences

- MP4/WebM/M4A recordings of any length can be transcribed once the image is rebuilt with ffmpeg (Phase B, plus the human's build-and-licence-check step).
- Image size grows by the Alpine `ffmpeg` package and its shared-library dependencies; not yet measured, not blocking.
- The licence check of the built image (GPL vs LGPL) is a human/lead gate, not a code dependency: no code depends on which `ffmpeg` build ships, and the ADR already states the LGPL-only static-build fallback if the distribution package turns out to be GPL.
- N worker replicas run up to N ffmpeg processes at once; no new concurrency control is added beyond the existing `concurrency: 1` per worker process.
- `apps/web`'s 24 MB upload cap for these three types is unchanged by this task (`apps/web/**` is out of bounds here); lifting it, and re-checking the 15-minute searchable budget for a long video through ffmpeg-chunking plus multi-piece Whisper transcription, is follow-up board task 11.4i.
- Whether GitHub's hosted CI runner has ffmpeg on `PATH` (so the opt-in tests run there, not just skip) is unverified by this task; the lead checks the next CI run's log and opens a small follow-up to install it in CI only if shown missing, without this task touching `.github/**`.
- **ffmpeg's own parser and memory-safety attack surface on untrusted media.** ffmpeg decodes bytes a teacher or student uploaded, over container and codec parsers with their own history of memory-safety bugs; this task does not vet ffmpeg's source, so it treats the binary as untrusted-input-facing and mitigates rather than trusts it: it runs as non-root (`USER node`, already the runtime stage's user, unchanged by this task), under a hard wall-clock timeout escalating from SIGTERM to SIGKILL (Decision §5) so a crash loop or hang can't persist or block the worker, with a running-total output-size cap against a decompression-bomb shape (Decision §5), and with `-protocol_whitelist file` plus a forced input demuxer (Decision §3) so a malformed or disguised file can only be mis-parsed as a local, static byte stream -- it can never make ffmpeg dial a network address or open a file the chunker didn't create itself.
- **Rollback:** `createFfmpegChunker` is additive and, before Phase B wires it into `createIngestGateway`, nothing calls it; reverting Phase A is free. After Phase B, removing the `chunker` option from `createWhisperTranscriber`'s call site restores the prior "refuse at upload" behaviour (11.4b) with no further contracts change, since nothing in `packages/contracts` changed for this task.
