## Open question: may a staff POST change an already verified or rejected teacher?
The review defaulted to "pending only; revoke is a future task." Checking the code: this is
**already shipped, decided and tested** from 8.1/9.3e, not a gap. `teacher-profiles.int.test.ts`
has two deliberately named tests exercising exactly this: "staff can later reject a verified
teacher" and "a re-verification does not lift the takedowns" (both still expected to pass); 9.3e's
own comment ("a later `verified` lifts nothing; staff lift each takedown explicitly") only makes
sense if a plain verify can target a non-pending teacher.

**Recommendation: no restriction.** A pending-only guard would revert already-decided, audited
behaviour (every transition writes a `teacher.verify` row with before/after, by a current staff
user, never the teacher themself — the audit trail is the safeguard, not a status gate). The
genuinely-missing "revoke" — reverting a decision back to `pending` — isn't possible today
(`VerificationInput` only accepts `verified`/`rejected`) and stays a separate future task if ever
wanted. Both phases add one doc comment recording this; no behaviour or test changes otherwise.

Mark as a **lead decision, not BLOCKED** (the PRD is silent here, and the existing tests already
settle it) — the handoff logs it `risk: high` since it touches `packages/db/src/repositories/**`
and `apps/web/app/api/staff/**`.
