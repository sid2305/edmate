# 3.9f plan — CLI chat on the db retrieval index (deferred from 3.9a, 3.9 Q3)

## Acceptance (verbatim, from docs/board/tasks.yaml)

> edmate chat retrieves from the db-backed index when a database is configured; a test shows the
> same-topic phrasing climbs the help ladder on the db index; no real model calls in tests.

How it will be shown: the gate output pasted into the handoff, plus a short paste of the new
integration test's pass line (vitest's own `Test Files`/`Tests` summary naming the file), and a
one- or two-line note of which exported functions the switch uses (`openDatabase`,
`retrievalIndexFor` from `@edmate/db`; `parseMarkdown`/`chunkDocument`/`indexDocument` from
`@edmate/ingest`) so the next reader can see no `packages/db` source changed.

## Background

3.9a deferred two items because `packages/db` was reserved for a concurrent task (3.9a handoff,
"Deferred" section; 3.9 handoff, Decisions): switching `apps/cli`'s `RetrievalIndex`
(`apps/cli/src/commands/chat/retrieval.ts`, an in-memory lexical adapter over
`@edmate/harness/testing`'s `memoryRetrieval`, built for the no-database Phase A composition root)
to the production db-backed index, and re-testing the "I still don't get it" same-topic ladder
(`apps/cli/src/commands/chat/sameTopic.test.ts`) on it.

**`packages/db` needs no change.** Everything this task needs is already public API:
- `@edmate/db` (its public entry, `packages/db/src/index.ts`): `openDatabase(env)` → `{ repos,
  close, ... }`, `retrievalIndexFor(repos, opts?)` (builds the production `RetrievalIndex` over
  `repos`, full-text only with no `opts.embedder`), `migrateDatabase(url)`.
- `@edmate/ingest` (its public entry): `parseMarkdown`, `chunkDocument`, `indexDocument` — the
  exact chunker `packages/db/test/recall.int.test.ts` already uses to turn the demo teacher's
  module notes into real `documents`/`chunks` rows through `repos.documents.create` +
  `indexDocument({ writer: repos.chunks }, ...)`. This task's int test copies that proven pattern;
  it is the only place chunk-writing logic needs to exist in `apps/cli`.
- `@edmate/db/internal` (public subpath, raw schema + `createDb`, for migrations/seed/tests only,
  per its own header comment) — needed **only inside this task's new integration test**, to seed a
  throwaway database's `users`/`courses`/`modules` rows directly, the same way
  `packages/db/test/recall.int.test.ts` and `apps/worker/test/ingest.int.test.ts` do. Production
  code (`dbRetrieval.ts`) never imports it — only `@edmate/db`'s public repositories.

No vector embedding is wired in this task: `retrievalIndexFor(repos)` with no `embedder` searches
full text only (confirmed sufficient for recall in `recall.int.test.ts`'s "full text only" case).
Embeddings for the CLI's db path are a follow-up, not needed to satisfy this task's acceptance.

## apps/cli's lint currently allows `@edmate/db/internal` (must change first)

`apps/cli/eslint.config.js` today uses `@edmate/config/eslint/base`, not `.../eslint/app`, because
`apps/cli` never imported `@edmate/db` before. `.../eslint/app` is the preset that bans
`@edmate/db/internal` from app `src/**` (comment in `packages/config/eslint/app.js`) and
`apps/worker/eslint.config.js` already shows the exact pattern this task copies: switch to the
`app` preset, then turn `no-restricted-imports` back off for `files: ['test/**']` so the new
integration test can import `@edmate/db/internal` to seed its throwaway database. This is an
`apps/cli` file, not a `.claude/**`/`.github/**` risky path.

## Files to create/modify (apps/cli only)

- `apps/cli/package.json` — add `@edmate/db` and `@edmate/ingest` to `dependencies` (production
  code uses their public entry only); add `pg` and `@types/pg` to `devDependencies` (the new
  integration test's own throwaway-database admin connection — exact versions pinned to
  `apps/worker/package.json`'s `pg`/`@types/pg`, which `apps/db` also pins).
- `pnpm-lock.yaml` — regenerated by `corepack pnpm install` after the `package.json` edit.
- `apps/cli/eslint.config.js` — switch from `@edmate/config/eslint/base` to `.../eslint/app`, with
  the same `{ files: ['test/**'], rules: { 'no-restricted-imports': 'off' } }` override
  `apps/worker/eslint.config.js` already has (copy, don't re-derive).
- `apps/cli/src/commands/chat/dbRetrieval.ts` (new) — production code:
  - `dbConfigured(env: Env): boolean` — true iff `env.DATABASE_URL` is a non-empty string.
  - `buildDbRetrieval(env: Env, teacherId: string, content: DemoTeacherContent): Promise<{ index:
    RetrievalIndex; close: () => Promise<void> }>` — opens `openDatabase(env)`; if
    `repos.retrieval.material({ teacherId })` is empty, seeds the demo teacher's chunks once
    (see below) before returning `retrievalIndexFor(repos)` and the handle's `close`. Auto-seed
    keeps "retrieves from the db-backed index when a database is configured" true for a human who
    only ran `db:migrate`/`db:seed` (which seeds the teacher/agent/packages, not chunks — confirmed
    by reading `packages/db/src/seed.ts`'s `SEED_TABLES`) before running `edmate chat`, with no
    second manual step. Document this auto-seed behaviour in a comment; it must insert nothing when
    material already exists (idempotent on a second `edmate chat` run, like `seedDemoTeacher`'s own
    `onConflictDoNothing` discipline — `documents.create` already errors on a duplicate id, so skip
    calling it at all when the check above is non-empty, not rely on conflict handling).
  - `seedChatChunks(repos: Repositories, content: DemoTeacherContent, teacherId: string):
    Promise<void>` (exported so the new test reuses it without duplicating logic) — for each module
    in `content.course.modules`: `parseMarkdown(content.notes.get(m.id), <title>)`, `chunkDocument(parsed,
    { headings: true })`, `repos.documents.create({ teacherId }, { id, moduleId: m.id, kind:
    'material', sourceTitle: parsed.sourceTitle, rightsDeclared: true })`, then
    `indexDocument({ writer: repos.chunks }, { scope: { teacherId }, documentId: id, source: {
    kind: 'parsed', document: parsed, headings: true } })` — exactly `recall.int.test.ts`'s
    `beforeAll` loop, generalised to any teacher id.
- `apps/cli/src/commands/chat/deps.ts`:
  - `buildChatDeps`: when `dbConfigured(opts.env)`, call `buildDbRetrieval(opts.env, teacherId,
    content)` and use its `index` for `deps.retrieval` (instead of `buildChatRetrieval(content,
    teacherId)`), and return its `close` on the new `ChatSetup.close` field; otherwise keep today's
    in-memory path unchanged and `close` is `undefined`.
  - `ChatSetup` gains `close?: () => Promise<void>`.
  - No change to `ChatDepsOptions`'s shape beyond what `ChatWorldOptions`/`env` already carry —
    `DATABASE_URL` travels through the existing `env: Env` field, so no new option is added
    (matches the acceptance's own wording, "when a database is configured", not a new flag).
- `apps/cli/src/commands/chat.ts` — call `await setup.close?.()` once `runChatCommand` is done with
  `setup` (after the existing `try { for await (...) } finally { process.off(SIGINT, ...) }` block,
  before `rl.close(); io.stdout('\nbye\n'); return 0;`), so the db pool always closes on a clean
  exit, `exit`, Ctrl+D or Ctrl+C. Note in the handoff whether the pre-existing `catch (e)` around
  `buildChatDeps` (line ~205) can ever leave a pool open on a thrown error (a close can only have a
  handle to close if `buildDbRetrieval` returned successfully, so this path is likely already
  safe — confirm, don't assume) — if it is unsafe, say so as a deviation/decision, not a silent fix
  bundled with no note.
- `apps/cli/src/commands/chat/deps.test.ts` — one added unit test: with `env: {}` (no
  `DATABASE_URL`), `buildChatDeps` still returns the existing in-memory retrieval behaviour (same
  scripted turn as the file's own existing tests) and `setup.close` is `undefined` — a fast,
  db-free regression guard that the no-db path is untouched.
- `apps/cli/test/chatDbRetrieval.int.test.ts` (new) — the acceptance test:
  - Postgres reachability + throwaway database (`createDatabase`/`dropDatabase`/`throwawayName`),
    copied inline the way `apps/worker/test/ingest.int.test.ts` already does (its header comment
    explains why: `packages/db/test/pg.ts` is an internal test-only file of `packages/db`, not
    published, so every other package's integration test duplicates the same small helper rather
    than importing it). `describe.skipIf(!up)(...)`; `CI === 'true'` and unreachable throws instead
    of skipping, matching the project-wide convention.
  - `beforeAll`: `createDatabase(dbName)`, `migrateDatabase(url)` (`@edmate/db`, public),
    `createDb({ DATABASE_URL: url })` + `createRepositories(db)` via `@edmate/db/internal` (this
    file is under `test/**`, where the eslint override allows it) to insert one teacher row, one
    course row and the demo course's module rows directly (the minimal subset
    `recall.int.test.ts` writes — not the full `seedDemoTeacher`, which needs a signed prompt-pack
    set this test does not otherwise care about), then call the new `seedChatChunks` to write real
    chunks for every module.
  - `afterAll`: close the handle, `dropDatabase(dbName)`.
  - One `it`: build `buildChatDeps({ env: { DATABASE_URL: url }, market: 'global', packageId:
    'free', source: 'teacher_preview', gateway: <scripted>, clock: slackClock(10) })` pointed at
    this test's own teacher id (not `CHAT_IDS.teacher`/`demo-teacher`, since `buildChatWorld` still
    hard-codes that id for the in-memory `AccessWorld` parts unrelated to retrieval — confirm this
    doesn't collide with the test's seeded teacher id, or seed under `CHAT_IDS.teacher` itself to
    avoid a mismatch between the world's `teacherId` and the db's scope; this is the one real
    plumbing risk in the plan — resolve it by reading `buildChatWorld`/`CHAT_IDS` again before
    writing the test, not by guessing). Run the three same-topic turns from
    `sameTopic.test.ts` ("What is a variable?", "Is a variable a name for a value?", "So is a
    variable just a name for a value?") through `runTurn`/`defaultSteps`, scripted gateway only
    (rule 4; no real model call — reuse or duplicate `sameTopic.test.ts`'s
    `scriptedChatGateway` helper; duplicating a ~30-line test helper across two files is an
    acceptable, reversible call here rather than extracting a shared one for a two-file reuse).
    Assert, per turn: no `error` events, no `locked` events, `events.at(-1)?.type === 'done'`; and
    by the last turn, the saved help state's `rung` is above 0 (same shape of assertion as
    `sameTopic.test.ts`'s own `withHelpStateReload`/`sessionState.saved` check — reuse
    `worldSessionStateStore`'s existing `saved` log the same way, since `deps.sessionState` is still
    the in-memory `AccessWorld` session store even on the db-retrieval path; only `deps.retrieval`
    changes in this task). Call `setup.close()` at the end (or in a `try/finally`) so the pool
    doesn't leak across tests.

## Gate

From the repo root, after `source ~/.nvm/nvm.sh`:

```
corepack pnpm install   # after apps/cli/package.json changes
corepack pnpm turbo run typecheck lint test --filter=@edmate/cli... --force --concurrency=1
python3 .githooks/secret-scan.py --all
```

Locally, `chatDbRetrieval.int.test.ts` needs Postgres reachable at `TEST_DATABASE_URL` (default
`postgres://edmate:edmate-dev@127.0.0.1:55432/edmate`); the shared dev Postgres is already
running there (lead note: never run `docker compose` or start, stop or recreate containers from a
builder worktree; export `TEST_DATABASE_URL` and run the test against it). Without it the test
skips locally (prints the standard `SKIPPED: no Postgres...` line) and is not required to pass
before handoff, but CI's `node` job already runs Postgres for every package (`.github/workflows/
ci.yml`'s single `TEST_DATABASE_URL`-backed job, confirmed) and will fail (not skip) if the test is
broken — say in the handoff whether it was run locally against a real Postgres, and paste the
result either way.

## No real model calls in tests

Both the new unit test and the new integration test use the scripted `ModelGateway` via
`ChatDepsOptions.gateway`, exactly as `chat.test.ts`/`deps.test.ts`/`sameTopic.test.ts` already do.
`apps/cli/test/setup/no-network.ts` backstops this (it blocks `fetch` only; a direct `pg` TCP
connection in the integration test is unaffected and is not a "real model call").
