# @edmate/harness

The turn pipeline and teaching engine. Pure TypeScript: it imports only `@edmate/contracts`, `zod`, `mathjs` and its own modules (build plan rule 3). Everything else (database, model gateway, queues) reaches it through the ports in `@edmate/contracts`.

## Pipeline order (`src/pipeline`)

```
admit → entitle → scrub (step 3, regex PII)
      → [ preGuard (step 3 checks) ‖ route ‖ buildContext ]   concurrent
      → escalate (distress)  ─────────────────────────────►  done → meter ‖ commit → trace
      → decide → generate → teacher_question? → postGuard → done → meter ‖ commit → trace
```

`runTurn(input, { deps, steps })` returns `{ events, finished }`. `events` ends with exactly one `done` or `error`; `finished` never rejects and lists background failures (meter, commit, trace, alert delivery). Timeouts, failure policies and the trace follow build plan § Turn pipeline spec; `STEP_SPEC` in `spec.ts` holds the numbers and the "On failure" text.

Determinism: `deps.clock` (`now`, `sleep`) and `deps.ids` are injected. Nothing in `src/` uses real timers.

## Step interface (`src/pipeline/types.ts`)

Each step takes a `StepEnv` (`input`, `deps`, `cancel`, `turnId`, `gateway`, `usage`, `report`) and returns a typed result; it never mutates shared state. The runner checks each result against a schema (`results.ts`); a result that fails counts as the step failing. Only `generate` gets an `emit` function, so event order never depends on scheduling. Steps report errors with meaning by throwing `TurnRejection(code)` (admit, entitle) or `TurnAbort(code)` (generate).

## admit and entitle (task 3.2)

- **admit** checks the input limits from `LIMITS` (text ≤ 4,000 code points and ≤ 8,000 UTF-16 units, ≤ 2 attachments, skill payload ≤ 16 KB of JSON → `input_too_large`) and then the rate limit (10 admitted turns per student per trailing 60 s → `rate_limited`, retryable; not for `eval`). It does not authenticate: the caller merges the signed-in `studentId` first.
- **entitle** resolves the entitlement server-side from `{ studentId, agentId, deps.entitlementSource }` only (client package, module or skill ids are never read), refuses `null`, paused and ended, loads the config through `deps.turnConfig` (ADR-0004: the session must be the entitlement's and open; the agent is at the session's pinned version; task 3.16: the session must also be pinned to the entitlement's package and version, else the store ends it, the db adapter clears the pair's last summary, and the load is `null`, so a student whose package or version changed starts a fresh session with no earlier history, sources or summary) and checks every object belongs to the entitlement (`src/access`). For subscriptions it then takes one message from the package's rolling 24-hour `dailyMessageLimit` (`limit_reached`). Any failure is `no_access`.
- **Limits** are in-memory sliding windows on the injected clock (`createTurnLimits(clock)`, built once by the composition root); a restart resets them and they are per-process, so they stay the default for tests (`testDeps`/`testSteps`), the CLI and evals. For a pilot, a composition root instead wires `@edmate/queue`'s `redisTurnCounter`/`redisTurnLimits` (task 3.14): a durable, shared `TurnCounter`/`TurnLimits` on Redis, one atomic Lua `EVAL` per `tryTake`, behind the exact same interface — no change here or in `admit.ts`/`entitle.ts`.
- **Testing:** `twoTeacherWorld()`, `memoryEntitlementStore(world, opts)` and `memoryTurnConfigStore(world)` mirror the db adapters (`entitlementStoreFor`, `turnConfigStoreFor`); `accessTurns()` runs turns through `runTurn` with the real admit and entitle.

## buildContext (task 3.4)

- Loads the learner profile (with `lastSummary`) and the last 40 messages concurrently, trims history oldest first to 16,000 UTF-16 units (the newest message is always kept, cut if it alone is longer), and builds one retrieval query from the latest message plus the latest agent message.
- Retrieval only through `RetrievalIndex.search(q, { teacherId, allowedModuleIds }, 5)`; every chunk returned is checked again and one outside the scope fails the step (`RetrievalScopeError`, the runner's `ask_teacher` fallback). `probe` runs over `lockedModuleIds` only (skipped when there are none) and only its `hit` is read. History plus chunk text stays within `MAX_CONTEXT_CHARS` (32,000; no tokenizer in the harness).
- Parses the session's raw help state (on `Entitled`, from `TurnConfigStore.load`, ADR-0005) with `parseSessionHelp`; anything invalid is rung 0 and `INITIAL_HELP_STATE`. The parsed `helpState` (with `answerKey`) stays out of `TurnContext`, events and traces; 3.6/3.8 thread it into decide and commit (`serializeSessionHelp`).
- **Testing:** `memoryRetrieval({ chunks, probe? })` and `retrievalWorld()` (allowed, locked and other-teacher chunks; out-of-scope text carries `OUT_OF_SCOPE_TEXT`).

## generate and the orchestrator (task 3.7)

- **Turn gateways (lead answer Q1).** After entitle the runner calls `deps.gatewayFor({ policy, billing })`, with billing `{ teacherId, packageId, studentId, turnId, source }` taken from the entitlement only. Guards get the agent's full policy; generate's primary attempt gets the policy without `fallback`; the retry runs with `tiers.main := fallback` (main again when there is none). The root binds `gatewayFor` to 2.4's `meterRouter` and returns `metered: true`, so that usage stays out of the `meter` step; a bare (test) gateway returns `metered: false` and its usage goes to `meter`. admit and entitle get a gateway that refuses every call. A `gatewayFor` that throws or returns something unusable gives a refusing gateway (fail closed).
- **Streaming.** `StreamReader` races each chunk against the cancel token, validates chunks with `ModelChunkSchema` and calls the iterator's `return()` (in the background, errors reported) when it stops early. The frozen port has no abort signal, so the provider sees the abort at its next chunk (Q5). Text passes a `StreamGate` (`deps.streamGate`; pass-through now, 4.5's sentence gate later).
- **Tools.** Offered only when the decision names them, they are in `deps.tools` and their skill is entitled (checked in decide and again in generate). Max 3 tool rounds, then a final call with no tools; a tool call on a call that offered none fails the attempt. Per round at most 4 calls, run in order; each needs JSON-safe args that pass `tool.input`, runs within 3 s, and its output must pass `tool.output` and stay under 4,000 JSON characters. Results go back as JSON envelopes (`{"tool_calls":…}` from the assistant, `{"tool_results":…}` from the user; Q4) with fixed error codes only. `present` turns an output into a `skill` event, dropped (and reported) unless the skill is entitled, the payload fits 16 KB and holds no do-not-say string.
- **Cost ceiling (Q2).** `deps.priceUsage` prices each usage as it streams; the trace and `done.usage` get it at once, failed attempts included. The turn total (step-reported usage at its own cost plus every priced call) aborts with `turn_cost_exceeded` when it goes over `deps.maxTurnCostMicroUsd` (default 100,000 = 0.10 USD) and refuses a new call once at or over it. Unpriced usage, or an invalid ceiling, also aborts.
- **Events.** `hint_rung` (hint, worked_example, solution) → `token`/`skill` in stream order → `sources` (only cited `[n]`) → `locked` (names the package only for `name_package`) → `teacher_question` → `replace` → `done`. Shown text is cleared with `replace ''` before a retry and before any error.
- **Cancel.** The consumer calling `return()` on `events`, or `RunTurnOptions.cancel`, stops generate at once with no retry; postGuard and teacher_question are skipped; the stream ends `error provider_error`; meter, commit (outcome `error`) and the trace still run.
- **TeacherQuestion (Q3).** For `ask_teacher` the runner calls `findSimilar` then `open` with the scrubbed text within 500 ms, sends `teacher_question` and sets `CommitRecord.teacherQuestionId`. A failure or timeout is reported and the turn still replies.
- **Logging (Q7).** Every `finished.background` failure goes to `deps.log.backgroundFailure` with the task, ids (logged only when valid ids) and the error's name; the message (cut to 300 characters) only for the harness's own `HarnessError` classes; never turn text.
- **SSE.** `formatSseEvent(e)` encodes one event; the web route is 9.4.
- **Testing:** `spyGateway(inner)` records requests, `gatewayFor` specs and iterator `return()` calls; `memoryToolRegistry`, `testTool`, `memoryTeacherQuestionStore`, `memoryTurnLog`, `stepEnvExtras()`.

## Guardrails (task 4.1, `src/guardrails`)

- **Phases and order:** `GUARD_ORDER` lists every guard per phase in the build plan's guard-table order: `scrub` (`piiScrub`), `pre` (`distressDetect`, `moderationIn`, `jailbreak`), `post` (`answerLeak`, `lockedLeak`, `grounding`, `adviceGuard`, `personaBoundary`, `tone`). That list decides run order; registration order never does.
- **Guard:** `{ name, phase, run(text, ctx, cancel) → { result: GuardResult, usage } }`. A factory closes over what the guard needs; `Ctx` is phase-specific and owned by each guard task.
- **Registry:** `new GuardRegistry<Ctx>(phase)`. `register` throws (`GuardRegistryError`) for an undeclared, duplicate, wrong-phase or malformed guard. `ordered()` returns the registered guards in declared order and skips ones not built yet; `missing()` lists those (4.9 adds the completeness test).
- **Chain:** `runGuardChain(registry.ordered(), text, ctx, { phase, clock, timeoutMs, cancel?, onGuardOutcome? })` never rejects. Outcomes:
  - `ok` with `text`: every guard passed on the final text.
  - `block` (`cause: 'verdict' | 'rewrite_unverified'`, `blockedBy`): a guard blocked, or the verification pass did not accept a rewrite. No `text`.
  - `escalate` with `text` and `alert`.
  - `failed` with `failure: { name, cause, errorName? }` (`empty`, `undeclared`, `out_of_order`, `error`, `invalid_result`, `timeout`, `cancelled`): the guards broke, so treat it like `block` (fail closed). No `text`, no raw error.
- **Verification pass:** when any guard rewrote, every guard runs once more on the final text; a rewrite or block there is `block` / `rewrite_unverified` ("rewrite once; else safe reply"). An escalate still escalates.
- **Time and cancel:** each guard has its own `timeoutMs` slice on the injected clock; the step's `cancel` token cancels the in-flight guard and fails the chain. The trace entries are `GuardTrace` (`{ name, ok, action? }`, action `failed` for framework failures, `(undeclared)` for an undeclared name), never reason or text.
- **Safety-event seam:** `onGuardOutcome({ name, phase, pass, outcome, cause? })` fires once per guard run; a throw or a rejected promise from it is ignored. Persistence (`safety_events`) waits for its ADR (lead answer Q1).
- **Wiring:** the `scrub` phase (4.2) and the `pre` phase (4.3) are wired (below). The `postGuard` step stub still fails closed; 4.5 wires its phase the same way when it lands the phase's first guard.

## PII scrub (task 4.2, `src/guardrails/piiScrub.ts`, `src/pipeline/steps/scrub.ts`)

- **What it removes:** phone numbers (fixed group shapes, flexible 7-13 digit groupings near a keyword or a `+CC`, spaced digits, spelled-out digits, a bare 10-digit number only next to a phone keyword), emails (also `[at]`, `(at)`, fullwidth `＠`, spelled-out "x dot y at z dot com"), Luhn-valid card numbers (dot/space/dash separated; a CVV or expiry — spaced, spelled-out or entirely unlabelled — only in the same message as one), OTP-like codes next to an OTP keyword (contiguous, spaced or spelled-out digits; "code"/bheja/aaya before or after the number), the student's own name after an introduction ("my name is", "mera naam hai", "मेरा नाम है", "name:"/"naam:", "मैं … हूँ", "I'm", "myself", "call me", "main … hoon"), and every `LocalePack.piiPatterns` match (Aadhaar-like, PAN and UPI ids come from the pack). Street addresses are out of scope. Each match becomes a placeholder: `[card]`, `[phone]`, `[id]`, `[otp]`, `[email]`, `[name]`.
- **Unicode:** a pre-pass (`src/guardrails/digitForms.ts`, task 4.2c, kept separate from the fold below so it doesn't conflict with 4.5's move of that fold to a shared helper) folds keycap, superscript and circled digit presentations to ASCII and drops marks that follow a digit. Matching then runs on a copy with every decimal digit folded to ASCII and invisible format characters shown as a space or dropped; the same spans are redacted in the original text.
- **Fail closed:** locale patterns compile with exactly `'gu'`; one that doesn't compile throws `PiiPatternError`, the chain returns `failed`, and the turn ends `guard_blocked`. The scrub runs to a fixed point, so `piiScrub` returns `ok` on its own output (the chain's verification pass).
- **Keyword windows:** bare 10-digit phones, flexible-group phones (no `+CC`), spelled-out numbers and OTP-like numbers count within 30 characters of a keyword, measured as the text will read after redaction (so the scrub settles in one pass however many numbers there are). Placeholders never count as keywords. Feeling, state, language and nationality words never count as a name. Constant digit runs ("9999999999") are never an id, card or phone just because of their length.
- **Raw-text distress check:** the runner calls `deps.distressCheck` on the raw input before the scrub and keeps only the boolean, which escalates at step 5. Nothing the scrub redacts can hide distress.
- **Step:** `scrub` scrubs `input.text` and every string (and PII-shaped number) in `input.skillPayload`. A value directly under a PII-named key (`otp`, `phone_number`, `studentName`, `upi-id`, ...) is redacted whole; `card`, `name` and `pin` alone are too generic (a flashcard, a file name, a map pin) and need a compound form (`cardNumber`, `studentName`, `pinCode`), and a PII-named key's object value does not propagate into its own unrelated nested keys. Any chain outcome but `ok` throws `ScrubFailedError` whose `cause` is `{ guardCause, errorName? }` only; the runner reports it on `finished.background` (`task: 'runner'`). Transcripts (2.7) arrive as `input.text`, so they are scrubbed the same way.
- **Attachments (task 4.2b): refused, not scrubbed.** A turn carrying any `input.attachments` (an image, per `@edmate/contracts`) is refused outright at the top of the scrub step, before the guard chain or the skill-payload walk runs and before anything about the attachment — not even its bytes or storage key — is read (`ScrubFailedError({ guardCause: 'attachment' })`). No OCR/vision pipeline exists yet (photo upload is P1 in the PRD); this is the safe stopgap until a real extract-and-scrub pipeline is designed and built for that task. The runner's raw-text distress check still runs first, so a distress hit on the accompanying text still escalates even when an attachment is present. `ATTACHMENT_REFUSED_REPLY` is a fixed, friendly English constant, exported but not yet wired to any client-visible channel (the wire `error` event carries no text field, same pre-existing gap as `DEFAULT_LIMIT_REACHED_REPLY`).
- **Testing:** `indiaLocalePackWithPii` / `IN_PII_PATTERNS` from `@edmate/harness/testing` (a stopgap until 3.10's real `content/locales/IN.yaml`, which must pass the same tests).

## distressDetect, preGuard and escalate (task 4.3)

- **Keywords (`distressKeywords.ts`)** are the single source of keyword truth. Every table (English, romanised Hindi, Devanagari) runs on every message whatever `lang` says. The text is matched in several normalised forms (format characters dropped and read as spaces, NFKD with Latin accents stripped, Cyrillic and Greek look-alikes, case, apostrophes, leetspeak, digit words, spaced or dotted letters, repeated letters), and written-together phrases are checked per word. `hard` = first-person intent, plan or method, or an abuse disclosure; `soft` = bare nouns, third person, past tense, vague farewells, or a hard phrase in a game context. Two combinations of soft phrases are hard: a method phrase (rope or noose, pills, blade, jumping off, poison, a roof) plus any other soft phrase, and a first-person vanish phrase plus a hopelessness phrase. `hasDistressKeyword` (hard only) is the implementation behind `PipelineDeps.distressCheck`; a composition root wires `distressCheck: hasDistressKeyword`. When preGuard fails, the runner also escalates on a soft phrase (`hasAnyDistressKeyword`).
- **distressDetect** (`pre` phase): a hard keyword escalates with no model call. Otherwise one small-tier classifier call (`{ distress: boolean }`) sees the message and up to 3 earlier student messages. Other soft keywords, alone or two at a time, ask the classifier; a soft keyword plus a classifier throw, timeout (230 ms, earlier messages awaited outside it) or bad output escalates, and so does a cancel before the call; with no keyword, a classifier failure propagates and the chain fails closed. The alert excerpt is at most 160 code points of the scrubbed text.
- **preGuard** builds `PreGuardCtx` (4.4's `moderationIn` and `jailbreak` reuse it and register in `defaultPreGuardRegistry`), runs the chain with a 300 ms slice per guard and maps `ok` / `escalate` / `block`; a `failed` chain throws `PreGuardChainFailedError` (no text), so the runner's own keyword check still runs.
- **escalate** always replies with `buildCaringReply(locale)`: `LAST_RESORT_DISTRESS_REPLY` plus the pack's helplines. It never uses the alert. English only for the pilot.
- **Testing:** `indiaLocalePackWithHelplines` (Tele-MANAS 14416) for the `distress/in` cases.
- **Testing:** `fakeGuard(name, phase, resultOrFn, { usage?, spy? })` from `@edmate/harness/testing`.

## Replacing a stub

Every step lives in its own file under `src/pipeline/steps/`. Until its task lands, a step throws `StepNotImplementedError`, so the runner applies its failure policy (admit, entitle and preGuard fail closed). To build a step, replace the body in its file and keep the `Steps['<name>']` type; `defaultSteps` picks it up.

## Testing (`@edmate/harness/testing`)

`virtualClock()`, `sequentialIds()`, `testDeps()`, `testSteps(overrides)` (happy-path doubles with a call log), `driveTurn(run, clock)`, the scripted gateway and the contracts fixtures. Tests never call a real model (rule 4).
